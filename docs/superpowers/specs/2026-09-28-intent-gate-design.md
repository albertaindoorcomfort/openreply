# Intent gate for campaign matching

OpenReply decides whether to DM a commenter by literal string matching: a campaign either fires on every comment (`matchAnyWord`) or on a keyword hit (`matchKeywords`, whole-word or partial). Neither knows what the commenter meant. On a furnace tune-up reel the real comments are "how much?", "do you do Airdrie?", "mine's making a noise" and "are you hiring" — no keyword catches the first three, and `matchAnyWord` DMs all four identically, including the job applicant. The intent gate adds one narrow semantic judgment at the existing matching seam: does this comment ask for what this campaign offers? Code keeps owning reach, dedup, rate limits, retries and sending. The model answers one yes/no question with a probability, and code thresholds it.

The judgment is supplied by TypeSafe's System One model (Jev) through `@typesafe-ai/sdk`. The dependency is optional in the same way Zernio is optional: an instance with no `TYPESAFE_API_KEY` behaves exactly as today. This is Unit 1 of two. Unit 2, lead triage and routing, reuses this unit's provider and state builder and gets its own spec after this ships.

## Boundary

`lib/utils/keyword-matcher.ts` is not modified. Three new modules live under `lib/matching/`, and a fourth, `lib/queue/campaign-matching.ts`, sits between the worker and them. `judgment-provider.ts` declares a `JudgmentProvider` interface with one method, `judgeIntents`, which takes a comment and a list of `{ campaignId, offer }` candidates and returns a probability per campaign id; it ships a TypeSafe implementation and a deterministic fake for tests, and it is the only module that imports the SDK. `intent-gate.ts` builds the state and questions from a comment and its candidate campaigns, calls the provider once, and returns a verdict per campaign: `pass` with probability, `reject` with probability, or `unavailable`. `match-campaign.ts` composes reach and meaning into the single result the worker consumes: it runs the existing keyword logic for every active campaign on the media, collects the survivors that have the gate enabled, asks the gate once for all of them, and returns per-campaign `{ matched, matchedKeyword, intentProbability }`. The worker never calls it directly. `resolveCampaignMatches` in `campaign-matching.ts` owns reading existing `DmLog` rows, the once-only rule described below, and the rejection and closure writes, and both worker paths call it.

The gate is a filter after candidate selection, never a replacement for it. Reach stays cheap and deterministic. Cost is proportional to comments that already passed a free test, and a provider outage can change only whether OpenReply acts, never which comments it considers.

The worker currently loops over active automations per comment and calls `matchKeywords` inside the loop, at two sites: the comment path and the inbound-DM path. Both are replaced by one call to `resolveCampaignMatches` before the loop; the loop then reads the precomputed result. This is what makes the judgment one request per comment regardless of how many gated campaigns are active on the post, rather than one request per campaign. `lib/polling/comment-reconciler.ts` keeps its own keyword prefilter untouched — it is a cheap reach test that decides what to enqueue, and the gate runs in the worker on what arrives.

## Campaign fields

Three additive columns on `Automation`, no enum, no backfill. `intentGateEnabled Boolean @default(false)`. `intentDescription String?` — a plain-language statement of what the campaign offers, written by the account owner, for example "a free furnace tune-up booking link for Calgary homeowners". `intentThreshold Float @default(0.7)` — the probability at or above which the gate passes. The server rounds the threshold to two decimals and bounds it to 0.50–0.95. Every existing row keeps the gate off and behaves byte for byte as before.

These compose with the existing fields to cover every useful behaviour. Keywords with the gate off is today's literal match. `matchAnyWord` with the gate on is real recall: the campaign considers every comment and DMs only the people who actually asked. Keywords with the gate on is precision on a noisy keyword: "info" hits, and the gate decides whether it was a request. The zod schemas in `app/api/automations/route.ts` and the import route gain one rule: a campaign with the gate on and an empty description is rejected at save. If such a row reaches the worker anyway, the gate treats it as closed.

## The question

One request per comment. State is a named object: `comment` with `text` and `authorHandle`, and `campaigns` keyed by campaign id, each carrying `offer` (the description). For each gated candidate the gate asks one Noul: does `comment.text` ask for, or express clear interest in receiving, what `campaigns.<id>.offer` describes? The `yes` criterion is that the commenter is requesting the offer or asking how to get it — price, link, booking, availability, "how do I". The `no` criterion is everything else, stated explicitly: general praise, an unrelated question, a complaint, a job or partnership inquiry, spam, a competitor, or a reply addressed to another commenter. Question ids are campaign ids and are for code; the full meaning is in each question's text and criteria.

The verdict is `pass` when the returned probability of yes is at least `intentThreshold`, otherwise `reject`. There is no "maybe" band. A Noul near 0.5 means the comment is genuinely ambiguous, not that the person half-wants the offer; ambiguity earning a human is Unit 2's job. The probability is recorded on the `DmLog` row in a new nullable column, `intentProbability Float?`, so thresholds are tuned from real data rather than guessed and so gated rows are distinguishable from keyword rows in the log.

The post caption is deliberately not in the state. It would sharpen the judgment, but `Automation` does not cache it and fetching it is an extra Graph API call per comment. The description carries the offer. Caption enrichment is a follow-up, not scope.

## What is sent to the provider

For a gated campaign, each request carries the text of the comment, the commenter's Instagram handle, and the campaign's offer description; if the campaign also replies to DMs, inbound direct-message text is sent the same way. Nothing is sent for campaigns that leave the gate off. `docs/setup.md`, the README and `.env.example` say so, and leave it to the operator to cover this in their own privacy notice and to check it against Meta's platform terms and local privacy law.

## What a rejection writes

A gate rejection is not a silent `continue`. It writes a `DmLog` row with `status: SKIPPED_NO_MATCH`, the comment text, and `intentProbability`. `SKIPPED_NO_MATCH` already exists in `DmStatus`, already renders in `components/status-badge.tsx` as "No match", and is currently never written by the worker; the gate gives it its meaning. A keyword miss continues to write nothing, exactly as today, so the only rows carrying this status are gate rejections, and `intentProbability IS NOT NULL` identifies them.

The row exists because of the reconciler. `lib/polling/comment-reconciler.ts` sweeps every five minutes across a 72-hour lookback, pre-filters by keyword, and re-enqueues every comment not in its handled set. For a `matchAnyWord` campaign with the gate on, a silent rejection would be re-enqueued and re-judged every sweep for three days — a paid call each time. So `SKIPPED_NO_MATCH` is added to the reconciler's `dmStopped` test and is treated as fully handled regardless of `publicReplyEnabled`, because a comment that did not ask for the offer must not receive the public reply either. `processComment` and the DM-trigger path short-circuit on an existing `SKIPPED_NO_MATCH` row the same way they do on `SKIPPED_PLAN_LIMIT`. A commenter who is rejected and then comments again produces a new comment id and is judged fresh.

A verdict is decided once per campaign and comment and then read from the row, never re-judged. A campaign with any existing non-rejection row proceeds from that row's stored values without a provider call, and a rejection write is create-only, so it can never overwrite another row. Two kinds of `SKIPPED_NO_MATCH` row exist. A judged rejection carries a probability, is final, and the reconciler treats it as handled. A closure, written when there is no key, no client, a key the provider refused, or no description, carries no probability and is not final: the reconciler keeps re-enqueuing it, at no cost because no provider call is made, so the comment is judged for real once the key exists and the worker has restarted. Treating judged rejections as handled matters for a second reason besides cost: sweeps are oldest-first and capped, so unhandled rejections would be re-enqueued every sweep and crowd genuine new comments out of the cap.

## Failure policy

The gate fails closed. This is a deliberate divergence from the follow gate, which fails open "so a real follower is never trapped." Failing open there gives away a link; failing open here DMs every stranger who commented on a `matchAnyWord` campaign, burns the 750-per-hour Meta budget, and risks the account. Different stakes, different default.

A provider error — network, 5xx, rate limit, timeout — surfaces from `match-campaign.ts` as a typed `IntentJudgmentUnavailableError`. `resolveCampaignMatches` catches it: campaigns for the comment that did not enable the gate are still served, gated campaigns get no row, and the job then fails so BullMQ's existing retry and backoff run. The existing per-`(automationId, commentId)` claims protect the already-served campaigns from a repeat send on retry. A failed job is recorded by the worker's existing failure handler, an `OperationalEvent` at `ERROR` and a worker alert per failed attempt, and it is never converted into a send. The client makes a single HTTP attempt with a five-second timeout per job, since BullMQ and the reconciler already own retries, so that volume is bounded. Because gated campaigns wrote no row, the comment has none for them, so the reconciler re-enqueues it on later sweeps within the lookback window. That is intended: a provider outage is exactly the case worth retrying, and when the provider recovers the comment is judged and handled normally. Inbound-DM jobs have no reconciler and are simply dropped on exhaustion, which matches how every other exhausted DM job behaves today.

A provider that refuses the request itself is different: a 400, 401, 403, 404 or 422 from the SDK surfaces as `IntentJudgmentRejectedError`, because a revoked key, missing access, an exhausted account or a malformed request is configuration, and retrying cannot fix it. `match-campaign.ts` catches it and closes every gated candidate with the reason `provider_rejected`; the error does not propagate. `resolveCampaignMatches` writes closure rows (no probability) whose message names the refusal, refreshes the message on an existing closure row, serves ungated campaigns, and the job completes successfully. A refused key or account (401, 403) pauses the gate for ten minutes at a time; a single request TypeSafe cannot process (400, 404, 422) closes the gate for that comment only. On a key or account refusal the worker logs once per process, and for ten minutes the provider refuses locally without an HTTP call, because closures are re-enqueued by the reconciler every five minutes and must stay free; after that window the next comment tries again, so an account that was only topped up recovers without a restart. Everything else from the SDK — connection failures, timeouts, rate limits, 5xx and unknown errors — stays `IntentJudgmentUnavailableError`.

If `TYPESAFE_API_KEY` is absent while any gated campaign is active, the worker records one `OperationalEvent` at startup and every gated campaign behaves as closed. A client that cannot be constructed closes the gate exactly like a missing key. The key is read once per process and memoized, so adding or changing it needs a worker restart. Non-gated campaigns are unaffected. The worker never crashes over an optional feature. `lib/env.ts` gains a `getTypeSafeApiKey()` that returns `null` rather than throwing, because absence is a valid configuration.

## Surface

The campaign form in `components/campaign-builder.tsx` gains a gate toggle, a description textarea whose placeholder teaches the shape ("A free furnace tune-up booking link for Calgary homeowners"), and the threshold under an advanced disclosure. The DM Logs view shows the probability on rows that have one. Both `app/api/automations/route.ts` and the import route accept and validate the three fields. All new strings are added in English and Traditional Chinese: English strings are the keys of `lib/i18n/zh-TW.json`, so each new string is one key with its translation, as `docs/localization.md` requires. `.env.example` gains a commented optional `TYPESAFE_API_KEY`. `docs/setup.md` gains a short section on enabling the gate and what it costs.

## Testing

Test-first in Vitest, all against the injected fake, with no Instagram, Postgres, Redis, API key or spend. Gate off yields a result identical to `matchKeywords` across the existing keyword fixtures. Gate on with probability at or above threshold matches and records the probability; below threshold rejects and records it. One comment with several gated campaigns produces exactly one provider call. A transient provider throw surfaces as `IntentJudgmentUnavailableError` and nothing is marked sent; a refused request closes the gated campaigns, writes closure rows and lets the job complete. An empty description is closed. A rejection writes `SKIPPED_NO_MATCH` with the probability, and the reconciler's handled test accepts that row; `processComment` skips a comment that already has one. The TypeSafe provider is tested against a stubbed client for the mapping from response to verdict, and for error classification using real SDK error instances: 400, 401, 403, 404 and 422 are rejections, while rate limits, 5xx, connection failures, timeouts and plain errors are unavailability, with the cause preserved in both. The ten-minute cooldown is tested with an injected clock, and so is its absence after a 400, 404 or 422, and client construction is checked for a single attempt and a five-second timeout.

One live fixture test against real Jev answers sits behind an environment flag and is run once after the account owner approves the first paid call; no paid call has been made from this workspace yet, and the test suite must stay green without it. Before a pull request, `npm run typecheck`, `npm run lint`, `npm test` and `npm run build` pass as `CONTRIBUTING.md` requires.

## Changes from the original design

The worker now calls `lib/queue/campaign-matching.ts` rather than `match-campaign.ts`, so the row reading and rejection writes live in one tested place that both worker paths share. Verdicts are decided once per campaign and comment, because re-judging on retries or sweeps would cost money and could flip an answer already acted on. Closures are recoverable rather than final, so comments held back for lack of a key are judged once it is configured. A provider outage no longer blocks campaigns that did not enable the gate, because failing the whole job would withhold DMs from campaigns that never needed the model. The server rounds and bounds the threshold so a stored value is always one the form could have produced. The client makes one HTTP attempt with a five-second timeout instead of the SDK's default retries, because stacked retries multiplied every failure and held a worker concurrency slot through the backoff. Provider errors are classified: a refused request (400, 401, 403, 404, 422) closes the gate with the reason `provider_rejected` and lets the job complete, and a refused key or account (401, 403) then makes the provider refuse locally for ten minutes so reconciler sweeps of those closures stay free, while a single unprocessable request closes the gate for that comment only; only transient errors fail the job. A closure row's message is refreshed when its reason changes, and the no-key message now reads "no usable TypeSafe key is configured" because it also covers a client that could not be constructed. The admin diagnostics list shows closures but no longer judged rejections, which are the gate working rather than a problem.
